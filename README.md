# 通知簿 · 校园通知执行 Agent

**把分散的校园通知，整理成有原文依据、可更新、能跟踪材料和完成情况的待办。**

通知簿是一个在自己电脑上运行的 Demo，适合学生、校园活动参与者，以及需要处理报名和材料提交的使用者。你可以粘贴通知或上传截图，核对内容后生成任务；收到后续通知时，在原任务上确认变更，保留之前的通知和完成记录。

本 GitHub 仓库当前发布项目介绍和使用指南，尚未包含可运行源码。下文启动步骤适用于已经取得完整项目源码的使用者。

> 当前状态：合成样例的完整任务流程可体验；真实截图识别和事项提取已接通，仍属试用功能。真实模型质量评估未通过，可能漏项、误读日期或翻译原文，所有结果都需要人工核对。

## 为什么做这个 Demo

校园事务常从一条群消息、一张截图或一份补充通知开始。真正费心的部分通常是：找回原文、记住截止时间、弄清要交哪些材料，以及判断后续通知是否改变了已经办完的事情。

例如，你看到了志愿者报名通知，准备了报名表并完成提交。几天后又收到通知：截止延期了，还要补交在读证明。原来的“已完成”待办，如果没有记录这次变化，就很容易漏掉新增材料。

通知簿围绕这些问题组织信息：

| 常见困扰 | Demo 提供的处理方式 |
| --- | --- |
| 通知分散，过后找不到要求的出处 | 保存原通知、截图和校正文稿，核对候选时可查看原文依据 |
| 截止时间和材料混在长消息里，容易遗漏 | 将已确认内容整理成任务、截止日期和材料清单 |
| 新通知来了，不知道该新建待办还是改旧待办 | 选择原任务，先查看变更预览，再确认更新 |
| 原来办完了，补充通知又增加了要求 | 保留旧完成声明，显示新增材料与“需复核”状态 |
| 材料备齐、实际提交和交给别人容易混淆 | 分别记录材料准备、用户完成声明和交接状态 |

这个 Demo 展示的是一种处理通知的方式，目前没有真实用户试点数据证明它能减少多少漏项或节省多少时间。

## 适合哪些场景

- **校园活动报名**：记录报名截止时间、报名表和后续补充要求。
- **材料提交**：逐项核对需要准备的材料，提交后留下自己的完成声明。
- **通知更新**：处理延期、新增或撤销材料、取消事项，保留之前的记录。
- **个人事务安排**：记录准备步骤，下载日历文件，或记下交接给联系人的过程。

当前是本机单用户 Demo。它不会自动报名、向学校提交表单、发送消息、付款或监听群聊；也没有多人共同操作的功能。

## 先体验哪一种模式

| 模式 | 适合做什么 | 使用前准备 |
| --- | --- | --- |
| **合成样例体验** | 熟悉创建任务、完成记录、通知更新和复核流程 | 安装并启动项目；无需 API Key，不调用模型 |
| **真实识别试用** | 尝试识别自己的截图、提取通知事项 | 启动者配置服务端模型 Key；需要联网及可用模型服务 |

建议第一次使用先走合成样例，再尝试自己的通知。页面中的“生成 mock 候选”是为固定样例提供的演示结果，**不代表真实模型的识别效果**。

## 启动 Demo

### 在已有运行环境中体验

如果启动者已经把 Demo 运行起来，在**同一台电脑**打开 [本地体验页面](http://127.0.0.1:3000/)。普通网页使用者不用安装开发工具，也不用在页面填写 API Key。

`127.0.0.1` 指当前电脑；这不是一个可以分享给其他人远程访问的在线演示地址。

### 自己在电脑上启动

准备完整项目源码、Node.js 22–24 和 npm 10 或以上版本。当前工程在 Windows、Node.js 24.16.0、npm 11.13.0 上验证；其他系统的完整启动流程尚未验收。

进入解压后的项目文件夹，在终端运行：

```powershell
cd campus-notice-agent
npm ci
npm run demo
```

随后打开 [http://127.0.0.1:3000/](http://127.0.0.1:3000/)。已经安装依赖时，只需运行 `npm run demo`。如果 3000 端口被占用，可运行：

```powershell
npm run demo -- --port=3001
```

此时使用地址 `http://127.0.0.1:3001/`。在终端按 `Ctrl+C` 停止服务。

演示数据保存在项目的 `data/demo/` 文件夹。停止或重新启动不会清空已保存的数据；演示模式与真实识别模式共用这份演示数据。已有库结构不兼容时启动会停止，请先备份，再按运行手册处理。

## 三分钟操作指南：报名、完成与补交材料

以下日期和材料都是页面内置的合成样例，不是真实学校通知。

### 1. 从原通知创建任务

1. 在“通知收件箱”右侧点击 **首次报名通知**。
2. 点击 **保存并审核文本**，阅读通知后点击 **确认文本无误**。
3. 点击 **生成 mock 候选**，检查报名事项、材料和日期；展开 **查看原文证据** 核对出处。
4. 点击 **预览提案**，确认将要创建的内容，再点击 **确认并创建任务**。

你会得到“校园志愿者报名”任务：截止为 **2026-10-23，含当日**，需要报名表。确认之前不会建立正式任务。

### 2. 区分“备齐材料”和“办完事情”

1. 在 **我的任务** 勾选报名表，表示材料已经备齐。
2. 展开任务的 **准备、交接与历史**。
3. 在演示中填写一段合成完成声明，例如“演示：已提交报名表”，再点击 **记录完成**。

勾选材料不等于已经提交。实际使用时，应在自己完成提交或办理后再记录完成；系统不会向学校核验这段声明。

### 3. 处理后续通知

1. 回到“通知收件箱”，点击 **延期并新增材料** → **保存并审核文本**，核对后点击 **确认文本无误**。
2. 在 **通知关系** 中选择 **更新：校园志愿者报名**。请在选择样例之后再选原任务，因为点击样例会重置这个选择。
3. 点击 **生成 mock 候选** → **预览提案**，核对截止改为 **2026-10-26**，并新增在读证明。
4. 确认更新，回到任务板查看结果。

原任务仍是同一项事务：报名表的准备状态、旧通知和旧完成声明继续保留；在读证明显示待准备，任务提示 **需复核**。准备新材料时，先勾选 **在读证明** 为已备齐；实际补交后，再填写新的完成声明并 **记录补充完成**。

### 4. 试试日期未知的通知

选择 **日期待确定** 样例，按相同流程确认。已知材料可以保留，截止日期会保持未知；日期未明确前不能导出日历，系统不会猜一个日期。

## 用自己的通知

### 启用真实识别：由启动者准备

首次配置时，把项目中的 `.env.example` 复制为 `.env.local`，在本机编辑：

```dotenv
MODEL_PROVIDER=glm
MODEL_API_KEY=填写你自己的模型服务密钥
```

文本型号 `MODEL_NAME`、视觉型号 `MODEL_VISION_NAME` 和服务地址 `MODEL_BASE_URL` 也需要与可用的 GLM 服务配置一致。模型是否可用及费用取决于供应商和账户，示例配置不保证始终可用。不要把 Key 写进 README、网页或提交到 GitHub；已有 `.env.local` 时直接编辑，避免覆盖现有配置。

先停止当前离线服务，再运行：

```powershell
npm run demo:real -- --check-config
npm run demo:real
```

配置检查不调用模型，也不显示密钥。打开页面后应看到 **真实识别已启用**。普通使用者不需要再提供 Key。

### 文本通知

选择 **粘贴文本** → 粘贴完整原文 → **保存并审核文本** → 核对并 **确认文本无误** → **提取通知事项**。

随后逐项核对事项名称、截止日期、全部材料及原文依据。检查完成后，先 **预览提案**，再确认创建任务。

### 截图通知

选择 **上传截图** → 选择 PNG/JPEG 图片（最大 10 MB）→ **保存图片** → **识别图片文字**。

对照原图核对识别文字，特别检查日期、时间、材料名称以及“新增”“取消”等措辞。有错误时编辑并保存校正稿，然后 **确认文本无误** → **提取通知事项** → 核对 → 预览 → 确认。

### 自己的后续通知

在原任务点击 **添加更新通知**，粘贴或上传新通知。这个按钮会选择原任务，但不会替你填写通知内容。核对并点击 **确认文本无误** 后，再次确认关联的原任务，再提取、核对差异、预览和确认更新。

### 如果识别失败或提案被阻止

草稿会保留。你可以检查网络和模型服务，或对照原图校正 OCR 文字，再重新审核、提取。不要为通过校验而猜填原通知没有写明的信息。

当前还没有完整的澄清作答和候选字段编辑界面。缺类别、关键问题未明确或证据检查失败时，部分通知无法继续生成任务。可以先保留草稿，或用合成样例体验完整流程。

离线模式可以保存、校正和审核自己的通知，但不会自动识别图片或提取任意通知。

## 几个容易误解的功能

| 功能 | 它表示什么 |
| --- | --- |
| 材料“已备齐” | 你已准备材料，仍需自己实际提交或办理 |
| “你已记录完成” | 保存你的完成声明，不代表学校已核验 |
| “需复核” | 新版要求发生变化，需要检查旧完成是否仍覆盖全部要求 |
| 联系人交接 | 记录本地联系人别名；系统不会联系或认证对方，记录已接受前旧负责人继续生效 |
| 导出 ICS | 下载日历文件后手动导入；日期变更或取消后需重新导出，并在自己的日历中检查结果，不保证自动同步或提醒送达 |

## 数据和隐私

通知、截图、校正文稿及任务记录保存在本机。**只有主动点击“识别图片文字”或“提取通知事项”时，相关图片或文本才会发送到配置的 GLM 服务，可能产生模型费用。** 点击保存、审核或预览不会发起模型调用。

真实识别默认关闭深度思考以减少等待，但仍可能超时或遇到服务不可用；关闭思考不能保证准确或成功。启动者可用服务端 `MODEL_THINKING` / `MODEL_VISION_THINKING` 设置控制，普通网页使用者无需处理这些参数。

所有任务生成与通知更新都先预览、再由本地用户确认。原通知和历次 OCR / 校正文稿保留为独立版本，后续更新不会抹掉旧完成记录。

发布到 GitHub 时不要上传 `.env.local`、数据库、用户截图或个人通知。备份和恢复操作见完整项目的 `docs/m6-runbook.md`。

本地应用已通过单元、临时数据库集成、离线场景、浏览器流程和生产构建检查；这些检查说明应用流程可复现，不能代替真实识别效果评估。

最新真实模型质量评估未通过：60 个计划版本中，2 个通过、32 个失败、26 个因前一版本失败而未运行。真实识别应按试用功能看待，暂不适合直接依赖它处理重要截止事项。

外部日历兼容性、宿主环境故障恢复及真实用户试点仍有未完成项。当前工程证据、失败记录与后续工作分别见完整项目中的 `docs/progress.md`、`docs/07-work-plan.md`。
