# Harness Engineering：一手资料与本项目落实

核对日期：2026-09-24。下列三篇正文均已通过官方网页读取；本文是中文摘述与设计推论，不是原文翻译。

## 1. 先区分两套 Harness

本项目有两个不同的被约束对象：

1. **开发 Harness**：帮助 coding agent 正确改仓库。包含可复现环境、仓库规则、任务卡、工具边界、验证命令、CI、变更证据和交接记录。
2. **产品 Harness**：让通知 Agent 在实际使用中可靠地读取通知、提出变更并维护任务。包含输入处理、结构化输出、验证器、持久化状态、权限、超时重试、审计、评估与恢复路径。

`AGENTS.md` 是开发 Harness 的规则入口。一个 prompt 或一份 Markdown 无法替代执行这些规则的程序、数据库约束、测试和 CI。当前目录中的设计材料是建设 Harness 的规格与起点；只有对应执行机制落地并通过验证后，才能声称该能力已实现。

## 2. 来源 H1：跨会话开发需要初始化、增量工作和可验证交接

- 标题：Effective harnesses for long-running agents
- 作者：Justin Young / Anthropic
- 发布日期：2025-11-26
- URL：https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents
- 类型与边界：工程实验报告，示例偏向全栈 Web 开发；不能把其结果当作所有领域和模型的效果保证。

**原文支持的事实**

- 仅有上下文压缩与高层提示不足以保证长任务可靠完成。文章观察到的失效包括一次尝试做太多、留下半成品、后继会话缺乏状态，以及过早宣布完成。
- 方案区分首次初始化会话与后续 coding 会话：初始化建立环境启动脚本、进度文件、初始 Git 状态和功能清单；后续会话逐项推进并留下结构化记录。
- 功能清单给出用户可观察的步骤，初始状态为未通过；通过测试后才改变状态，避免通过删除或弱化标准来制造成功。
- 后续会话先检查目录、Git 历史和进度，运行基础验收，再实现下一项功能。仅有局部测试仍可能遗漏端到端错误，文章使用浏览器自动化补充验证。
- 原文明确说，多 Agent 是否优于跨会话的单个通用 Agent 仍是开放问题。

**本项目的设计推论**

- 首次开发先完成环境与一条最小端到端流程，例如“导入文本通知→生成待确认草案→用户确认→任务板显示”；不要从同时构建全部页面和集成开始。
- 每张实现任务卡只要求一个可演示的行为切片，写清输入、已有状态、期望状态、非目标、相关文档、执行命令与验收证据。
- 每次交接记录：完成的任务 ID、变更文件、真正运行的命令与结果、未解决问题、当前数据迁移状态、下一步入口。失败和未运行的测试必须保留原状态。
- Windows 项目提供可直接运行的 PowerShell 命令，并维护 lockfile、环境变量示例与确定的运行时版本。文章中的 `init.sh` 是一种实现，本项目不必照搬脚本语言。
- 不为体现“Agent”而引入多 Agent。先使用确定性流程编排，将模型限制在提取、关联候选、变化解释等需要语义判断的位置。

## 3. 来源 H2：评估对象是模型与 Harness 的组合，完成要看真实状态

- 标题：Demystifying evals for AI agents
- 作者：Mikaela Grace、Jeremy Hadfield、Rodrigo Olivares、Jiri De Jonghe / Anthropic
- 发布日期：2026-01-09
- URL：https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents
- 类型与边界：工程实践综述；其中任务规模、指标和案例不是本项目已经获得的实验结果。

**原文支持的事实**

- Agent Harness 处理输入、编排工具调用并返回结果；评估 Agent 时评估的是模型和 Harness 的组合。
- 一个 eval 需要任务、独立尝试（trial）、评分器、执行轨迹和最终环境状态。文章将“声称订票成功”与“数据库中实际存在预订”明确区分。
- 评分器可以是代码、模型或人工；能用确定性检查的地方优先使用代码。模型评分需要清晰标准和人工校准。
- 能力评估用于探测当前还做不好的任务；回归评估用于保护已经稳定的行为。随着能力稳定，可将案例纳入持续回归集。
- 每个 trial 应从干净、隔离的环境开始；残留文件、缓存或前次运行信息可能污染结果。应同时覆盖某行为“应发生”和“不应发生”的案例。
- 多次尝试至少成功一次与每次都成功是不同可靠性问题。模型的非确定性要求保留重复试验，而不是挑一次漂亮结果。
- 文章建议从 20–50 个真实失败或日常手测场景起步，并强调阅读失败轨迹、检查评分器本身和持续维护测试集。
- 自动 eval 不能代替全部用户研究；完整质量视图还包括生产监测、反馈与人工复核。

**本项目的设计推论**

- 任务一致性的主评估对象是数据库最终状态与审计链：原任务是否被正确更新、无关任务是否保持原状、旧通知是否保留、新增材料是否出现、责任与完成证据是否仍有效。不能只评分回复是否听起来合理。
- 正例与负例成对准备：同一活动延期应更新；同名不同学院活动不应合并；明确取消应标记取消；来源不明的“可能取消”应进入澄清。
- 将“提取是否正确”“事件关联是否正确”“变化应用是否正确”“用户是否顺利校正”分开评分，避免一个平均分掩盖错误更新。
- 运行模型 eval 时固定输入、接收时间、时区、已有任务状态、模型版本、prompt 版本和 schema 版本；每次使用独立临时数据库。记录失败原因和样本数。
- 采用两类运行：无模型的确定性回归检查在每次变更运行；真实模型质量评估在模型、prompt、关联规则或 schema 改动时运行。Mock 通过不能代表真实 OCR/模型效果。
- 对延期、误合并、重复上传、取消、已完成任务遇新增要求等高影响案例重复运行，报告首次成功率及重复一致性，不以“多跑几次总会成功”作为准入条件。
- 用户反馈进入闭环：保存经授权脱敏的失败样例→判定是产品错误还是标注歧义→补回归案例→最小修复→跑相关集和保护集→人工检查轨迹→再发布。

## 4. 来源 H3：AGENTS.md 是有发现规则的分层入口

- 标题：Custom instructions with AGENTS.md
- 发布方：OpenAI Developers
- URL：https://developers.openai.com/codex/guides/agents-md
- 类型与边界：Codex 官方配置文档；规则随产品版本可能变化，不代表所有 coding 工具都会自动读取该文件。

**原文支持的事实**

- Codex 开始工作前构建指令链；全局规则与项目规则按发现顺序合并。
- 项目范围从项目根沿路径走到当前目录；每层优先读取 `AGENTS.override.md`，再读 `AGENTS.md`，再尝试配置的备用名称。每个目录最多选择一个文件。
- 更接近当前目录的指导内容在合并文本中更靠后，可覆盖较上层指导。无项目根时只检查当前目录。
- 默认的合并文档大小上限是 32 KiB。其他文件名需要配置为 fallback 才参与自动发现；不能假定单数 `agent.md` 会自动生效。
- 文档给出检查已加载指令、处理 override 冲突、重启会话重新加载等验证办法。

**本项目的设计推论**

- 根目录采用标准名称 `AGENTS.md`。入口保持简短，列出业务不变量、工作顺序、验证命令与文档索引；详细设计存于独立文档。
- 根入口明确要求按任务阅读对应的架构、数据契约、评估和运行说明；仅放一个链接不等于模型已经读取其内容。
- 不默认在所有子目录复制一整份指导。确有不同约束时才建立局部文件，并检查实际运行目录及发现结果，避免隐藏覆盖。
- 新会话先报告当前任务、适用规则与验收条件；避免依靠上次聊天记忆维持正确性。

## 5. 项目必须建设的 Harness 要素

以下是根据来源形成的**项目规格**，不是对任何一篇文章的逐项复述，也不表示这些机制已经实现。

| 要素 | 必须留下的信息或机制 | 可检查的完成证据 |
| --- | --- | --- |
| 环境与复现 | 运行时版本、lockfile、安装/启动/验证命令、配置示例、迁移与种子数据、外部依赖开关 | 新目录安装后可运行最小流程；缺少配置时明确失败 |
| 上下文与状态 | 短 `AGENTS.md`、需求与非目标、领域术语、不变量、架构决策、任务卡和交接记录 | 新会话能找到下一项任务并复跑上次验证 |
| 输入边界 | 截图作为不可信数据；记录文件类型/大小、来源、接收时间、OCR 版本、原文定位；来源未知显式记录 | 恶意通知文本不能改变系统权限、调用工具或覆盖开发规则 |
| 模型契约 | 受 schema 约束的候选结构、未知值、置信与证据定位、拒绝/澄清出口、版本信息 | 错误 JSON、缺少证据、矛盾日期进入验证失败或澄清状态 |
| 工具与权限 | 最小读写工具、参数验证、用户/工作区隔离、数据库事务；模型输出只作候选；应用变更由服务校验 | 越权、跨用户读写、未确认的高风险变更被服务层拒绝并留审计 |
| 预算与恢复 | 请求超时、重试条件和次数、单任务调用预算、幂等键、取消与失败状态、断点恢复 | 超时不留下半个任务；重复回调不产生重复变更 |
| 可观测性 | request/run ID、阶段、模型/prompt/schema 版本、耗时、token/费用（可取得时）、输入输出摘要、验证与应用结果 | 能从错误任务追到来源、候选变更和失败阶段；日志不含密钥或无必要的原图全文 |
| 评估与回归 | 场景、初始状态、预期结果、判定器、负例、固定测试时间与独立数据库、真实模型运行记录 | 错误更新、漏项与歧义处理可计数；失败集能稳定重现 |
| 反馈与维护 | 用户校正原因、错误分类、回归样例、变更前后结果、文档/规则漂移检查 | 一次真实失败被转为保护用例，修复后仍保护其他已通过行为 |
| 长任务交接 | 每次只推进一个切片；保存实际完成项、当前风险、命令结果和下一步 | 中断后无需猜测即可继续；未实现项不会被标成完成 |
| 交付与发布 | Definition of Done、检查结果、迁移兼容性、可回退版本、导出兼容性及局限说明 | 有演示与测试证据；检查失败时不会发布或声称通过 |

此处“最小权限、输入注入边界、事务和幂等、隐私日志”是本项目针对通知输入和持久化写入提出的工程要求；上述三篇资料不是它们的完整安全规范。后续实现仍需检查所选框架、数据库和模型供应商的官方接口与安全要求。

## 6. 本项目的最小闭环示例

1. 输入通知 A：“周五前提交报名表”，记录原图与文本证据。
2. 建立任务草案并确认，保存通知关联、负责人和任务版本。
3. 输入通知 B：“延期至周一，增加证明”，先判断是否为同一事项；证据不足则澄清。
4. 提交候选变更：截止日期变化、新材料、受影响的准备安排。变更应用前校验预期任务版本，避免覆盖并发修改。
5. 在事务中追加变更记录并更新当前投影；若未满足新增前置条件，应显示待处理项。提醒发送记录独立保存，不能据此标记完成。
6. eval 检查任务数量、截止日期、材料集合、版本与来源、历史状态和完成条件；浏览器验收用户确实能理解变化并校正。
7. 发现错误后，以该通知序列建立可重放案例，记录修复及回归结果，再推进下一项能力。
