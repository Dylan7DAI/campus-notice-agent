# 小步开发任务卡

默认路线：先证明任务一致性，再补识别体验。每次 coding 会话只做一张卡或卡内明确子任务。以下全为 TODO；完成状态以 [progress](progress.md) 中的实际证据为准。

## M0：可复现环境与执行框架（约2–3个工作时段）

- 目标：任何新会话能安装、启动、验证并知道做到了哪里。
- 读取：AGENTS、架构、Harness。修改范围：package/lock/tsconfig/lint、最小 src/app、CI、配置校验、README运行区、progress。
- 实现：核实并固定兼容版本；127.0.0.1开发服务；strict TS；空领域边界；配置缺失清晰报错；mock模式标识；基础CI。安装与生成不覆盖本包文档。
- 验收：`npm ci`、`npm run check`、`npm run build`成功；浏览器页面显示当前是开发壳；缺配置不会伪造模型连接成功。此卡不要求产品tests/evals通过，也不能放空测试冒充。
- 不做：OCR、数据库业务、模型集成、复杂页面。交付：准确版本和启动记录。

## M1：领域对象、数据库与事务底座（约3–4个时段）

- 目标：材料、完成、交接、版本能被代码严格表达。
- 读取：领域、契约、schemas。修改范围：domain、application ports、contracts、prisma、infrastructure/db、unit/integration。
- 实现：实体与外键、Due/证据校验；Task完成覆盖和交接状态；临时库迁移/seed；CommandResult与CAS事务；固定Clock；稳定ID。
- 验收：E06/E07/E08/E09/E14/E15/E16对应核心测试先写后跑；事务故障注入后所有表均保持原状态；同幂等请求只出现一次提交。新建/清理只触碰测试目录。
- 不做：真实模型/界面。交付：测试命令与数据库约束说明。

## M2：无模型的完整主路径（约3–4个时段）

- 目标：粘贴通知→审核文本→mock候选→预览→确认→任务板，用户可独立操作。
- 读取：产品、契约、领域证据规则。修改范围：routes、UI、intake命令、mock adapter、private storage、E2E。
- 实现：单图/文本上传、格式限制、不可变TextRevision、片段证据目录、关联已有事项/新建、阻塞澄清、可保存草稿；实现自述完成入口。
- 验收：Playwright验证主路径、刷新后草稿保留、原文可打开、缺证据无法提交、当前mock清楚可见。无真实模型也能演示数据闭环。
- 不做：把mock叫智能识别、多图拼接、外发。交付：浏览器验收记录，截图只用合成文本。

## M3：通知变化后的任务一致性（约4–6个时段，核心里程碑）

- 目标：后续通知正确更新同一任务，并指出完成/准备/交接缺口。
- 读取：领域全文、全部E场景、API。修改范围：domain diff/impact、apply及准备/交接命令、预览UI、最小真实ICS编码器、离线eval runner。
- 实现：延期/提前、增删要求、乱序与冲突、稳定要求ID、完成epoch、计划冲突、取消/恢复、补偿提案、CAS与幂等错误界面。禁止自动重排用户计划。
- 验收：E01–E24全部有真实runner断言；E18/E19用故障adapter注入验证真实错误处理，E21使用实际ICS编码器并解析结果，不用mock宣称编码通过。真实模型质量和外部日历客户端成绩仍未验证；单元+集成+主E2E通过；真正NO_CHANGE无多余版本，新增来源即使字段未变也保留关系；任务T1不会变成重复T2。
- 不做：自由多步Agent或自动提交。交付：summary中每例actual对照expected，未适配case必须标not_run而非pass。

## M4：受约束的真实视觉识别与提取（约3–5个时段）

- 目标：真实截图经过审核、结构校验和证据链进入既有一致性流程。
- 读取：Harness预算/安全、契约、评估。修改范围：model adapters、版本化prompts、AgentRun状态、eval:model。
- 实现：一种当前可用provider；明确配置和图像外传说明；timeout/cancel/3次总预算；无效JSON一次修复；证据片段白名单；输出拒绝路径；run持久化；本地provider可选不作为默认成功路径。
- 验收：30序列语料划分与标签留档；真实图像评估、负例注入、timeout/中断/错误结构测试；离线回归仍全通过；mock结果与真实结果分开报告。
- 不做：自动选择所有供应商、基于模型置信度跳过确认。交付：模型/提示/schema版本、样本数和真实评估局限。

## M5：准备、交接和日历可用性（约3–4个时段）

- 目标：用户能理解事情卡在哪里，并导出准确日历。
- 修改范围：准备/交接页面、calendar adapter、任务详情历史、相关测试。
- 实现：完善准备/依赖和交接界面，接通M3已建立的领域命令及ICS编码器；展示date-only/instant、稳定UID/SEQUENCE、取消文件和stale提示。模型不推测证明办理时间，不重复建立另一套状态与导出逻辑。
- 验收：E08/E09/E20/E21真实API与UI链路；至少两个实际客户端/解析器的导入试验（记录具体客户端和版本）；明确记录重复导入/取消是否被客户端遵守，不能通过文件语法推断客户端行为。
- 不做：持续同步或后台送达保证。交付：ICS兼容性和局限记录。

## M6：数据保护、故障恢复与本地交付（约2–3个时段）

- 目标：试用时出错可恢复，原图/密钥不泄漏。
- 修改范围：输入保护、日志、备份/恢复、删除、运行手册、完整CI。
- 实现：目录校验/Origin检查/上传限制、run中断恢复、脱敏trace、删除说明、SQLite与附件一致性备份；键盘/窄屏/空态/错误态检查。
- 验收：备份恢复后任务与证据引用一致；无真实正文进入日志/Git；中途断电模拟不造成半提交；完整check/unit/integration/E2E/build通过。至少一份可复现本机安装记录。
- 不做：未经授权公网部署。交付：故障演练和已知问题清单。

## M7：小规模用户试用与下一轮决策（视招募和标注另排）

- 目标：验证漏项、错误更新和校正时间，而非仅收集“觉得方便”。
- 按评估文件执行8–12人试点，固定素材、条件和顺序；记录退出/失败，不删不利结果。
- 验收：匿名结果、分母/配对差值/失败分类、至少三项观察到的设计问题；将缺陷转回归场景；决定继续/缩小范围/暂缓。没有数据则明确未完成，不写虚构提升百分比。

## 每张卡的统一 Done 条件

相关可见行为可复现；要求命令真实执行并保留结果；无新增关键不变量失败；schema、API和UI一致；失败/未运行明确；不混入无关重构；progress和下一步更新。遇跨度过大的卡可拆为M3a/M3b等，但保留原验收集合和依赖关系。
