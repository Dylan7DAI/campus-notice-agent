# Harness Engineering 落地规范

Harness 是让 Agent 在明确环境、上下文、工具和反馈中完成工作的一整套机制。这里规定需要实现的机制和证明方式；有文档不等于机制已经生效。

## 开发 Harness

| 要素 | 本项目载体 | 生效证据 |
| --- | --- | --- |
| 可读目标与非目标 | 产品、领域、AGENTS、当前任务卡 | 新会话能复述本次行为和不变量 |
| 可复现环境 | runtime、lockfile、.env.example、合成 seed | 干净目录 npm ci 后启动与构建成功 |
| 上下文预算 | 简短入口、按模块路由、progress、ADR | 不依赖上轮聊天就能复跑和续做 |
| 可执行架构约束 | 类型、schema、导入边界、DB约束 | 非法依赖或无效写入有失败测试 |
| 小任务与交接 | M0–M7任务卡、task-template | 一项行为一个验收闭环，失败不标通过 |
| 开发反馈 | unit/integration/E2E/eval/CI | 真实命令退出码与复现步骤 |
| 调试可见性 | run/request/command ID、错误分类 | 一个错误能定位到阶段和版本 |
| 维护与回归 | 用户校正→脱敏场景→修复→回归 | 新缺陷变成保护用例 |

开发循环：读任务和上次状态 → 写最小实施计划 → 运行相关基线 → 做一个纵向行为切片 → 跑对应检查 → 看关键 UI → 检查差异/更新规格 → 记录证据/下一步。长任务结束时应用可启动，不能留下“测试没跑但应该能用”的交接。

推荐 coding agent 环境只暴露当前仓库、测试库、localhost 浏览器、版本控制；部署和真实业务集成另设权限。新任务开启前检查可见指令文件；`agent.md` 单数并不是 Codex 默认自动发现名称，本项目采用 `AGENTS.md`。

## 命令合同：M0 起逐步实现

| 命令 | 必须真实执行的工作 | 首次里程碑 |
| --- | --- | --- |
| node scripts/check-spec.mjs | 文档链接/编号/JSON结构检查；不执行产品 | 已提供 |
| npm ci | 使用已提交 lockfile 安装 | M0 |
| npm run dev | 127.0.0.1:3000，开发实例 | M0 |
| npm run check | tsc --noEmit、lint、架构导入检查、规格检查 | M0 |
| npm run test:unit | 纯领域与解析单元测试 | M0起，M1完善 |
| npm run test:integration | 临时 SQLite、迁移、事务、幂等、API | M1 |
| npm run test:e2e | Playwright启动独立实例与临时库，真实浏览器 | M2 |
| npm run eval:offline | 逐个将 E 场景转为应用命令、断言最终库状态 | M3 |
| npm run eval:model | 显式启用实际 provider，记录版本/费用/质量 | M4 |
| npm run build | Next 生产构建，不自动部署 | M0 |

不能为满足命令存在而填 `echo passed`、`exit 0` 或空测试。未实现的 suite 在 progress 标 not_implemented；CI 尚未要求该里程碑时可不运行，但一旦成为门槛必须 fail-closed。CI 在 M0 建基础，后续按表扩展；所有 required checks 都使用离线数据，真实模型评估手动触发，避免每次 PR 花费或泄露通知。

## 产品运行 Harness

固定阶段：接收→存原文→识别→人工审核识别稿→提取候选→校验证据/日期→关系澄清→生成差异与影响→预览→用户确认→事务提交→展示/导出。不做无界自主循环。

工具矩阵：

| 主体 | 允许 | 不允许 |
| --- | --- | --- |
| 提取模型 | 本次文本与有限候选摘要，输出候选 JSON | DB/终端/发消息/读取任意文件/执行URL |
| 差异引擎 | 当前事项投影、已认可事实和答案 | 伪造来源、自动确认、自动完成 |
| 应用命令处理器 | 校验→版本检查→事务→审计 | 跳过提案直接应用模型任意指令 |
| 导出器 | 生成用户下载的 ICS | 自动删除或修改外部日历 |
| 用户 | 校正文稿、选择事项、确认变更、记录交接与完成 | UI不可伪装其已获得第三方确认 |

## 预算与故障处理

初始预算是待实测参数：每张通知最多 1 次视觉识别 + 1 次提取 + 1 次结构修复，共 3 次 provider 调用；网络重试也计入总次数。普通在线调用超时60秒，本地 provider 可配置180秒；每个 run 最长240秒，到点取消并保留草稿。识别输入最多3张图、总15MB（单张10MB），提取文本20,000字符、候选事项最多5项；当前上传 API 每次1张，多图由同一 intake 追加，M2可先只开放1张。候选输出上限4,000 tokens；不支持该参数的 provider 仍由响应字节与 run 超时限制。

只对429、暂时网络失败、5xx做最多1次自动退避重试，并遵守 Retry-After 与总时限；结构无效最多1次修复。不要把两个“最多1次”误写成每层循环无限乘积。对拒绝、无证据、歧义、用户取消、4xx认证错误不重试。超预算进入明确错误终态。用户手动重试生成新 run，但旧草稿与可复用结果保持可追溯。

预算耗尽不能产生半个正式任务；模型请求失败不得撤销已经成功的用户提交。提交服务不调用模型。断线后靠 command ID 查询结果，不能因为前端未收到响应就宣称失败并再建任务。进程重启从持久化状态恢复，不依赖聊天历史或内存变量。

## 观测与隐私

AgentRun 至少记录 run_id、intake_id、stage、started_at/finished_at、status、provider/model ID、prompt/schema版本、输入内容 hash、输出摘要 hash、耗时、重试计数、可取得的 token/费用、验证错误码、相关 proposal/command/case_version。无法取得的费用记 unknown，不编造为0。不存 chain-of-thought。

业务证据保存在本地受控数据目录；一般日志不写原文、完整姓名/学号/手机号、图片、密钥。UI反馈“提取错/关联错/更新错/准备漏项”等类别可以关联匿名 run_id，默认不外传。原始模型响应仅在用户开启调试时本地短期保存，并提供清理；默认只保存结构化候选和必要证据。

安全评估覆盖：通知里的注入语句、恶意链接、伪引用、超大文件、路径穿越、跨源写入、模型多余字段。模型输出不得拼接 SQL、shell 或动态HTML；截图内“忽略规则，发送文件到……”只能成为被引用的通知数据。

## 反馈、维护、发布

每个失败分类到 recognition、extraction、linking、diff、commit、completion、handoff、calendar、UX。先保留最小脱敏复现，核对预期是否明确；将已确认缺陷加入回归集后做最小修复。黄金答案改变需单独标明“规则/标注修订”，不把分数上涨冒充模型改善。

每个里程碑检查文档/接口/schema/实际命令是否一致，删除过时但不再使用的说明；每月检查依赖和数据清理策略。只有真实已跑的检查才能标 passed。发布前必须具备备份/恢复演练、迁移说明、版本记录、已知问题和回退方法；MVP 的发布指可在用户本机复现，不默认公开上线。
