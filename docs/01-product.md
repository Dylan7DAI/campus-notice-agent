# 产品、差异点与交互框架

## 用户问题与假设

目标用户是独自管理校园事务的学生。首轮只处理报名、材料提交、活动变更三类通知。输入为用户主动上传的 PNG/JPEG 截图或粘贴文本；先不抓取群消息。真实风险包括材料缺失、把旧通知当最新版、已交给别人但无人接手、把提醒或准备误认为完成。

待验证假设：有证据的变更预览、要求覆盖检查和明确的交接状态，能比普通任务清单减少漏项和错误更新，并降低用户纠错时间。不得声称“首创通知 Agent”；领域差异点是通知变更如何影响执行状态，研究贡献要靠比较结果证明。

## 最小产品边界

必须有：截图/文本输入；可校正的识别结果；事项候选匹配与新建选择；澄清；字段级证据；变更前后对比；任务板；材料清单；用户安排的准备计划及冲突提示；负责人别名和交接记录；手工完成声明/附件；ICS 下载；版本历史和失败恢复。

不做：自动提交/自动报名、支付、读取账号群聊、医疗判断、自动联系负责人、真实多人权限系统、持续日历同步、智能优化整周日程、依靠通知文字认定外部办理成功。提醒 MVP 仅做站内“待处理”和用户自选 ICS 提醒，不保证浏览器关闭后送达。

## 主路径：周五改周一，增加证明

1. 用户上传“材料于 2026-09-25 17:00 前提交，需报名表”。原通知 N1 保存；提取任务“提交材料”和要求 R1“报名表”。
2. 用户确认，产生任务 T1；可设准备计划 P1“周四晚打印报名表”。系统提示完成须由用户确认提交，打印完成不等于提交完成。
3. 用户上传同事项 N2：“截止延期到 2026-09-28 17:00，并增加在读证明”。系统提出关联 T1，展示两处变化和证据。
4. 用户确认后 T1 ID 不变；R1 准备状态保留，R2 新建且未满足；检查开证明的准备时长是否可安排。没有用户填写的办理耗时/开放时间时，提示信息缺失，不捏造办公室开放时段。
5. 旧 ICS 标为过期，提供新版下载。完成记录若只覆盖 R1，则卡片显示“新增要求待复核”，保留之前提交的历史证明。

## 五个页面 / 面板

| 页面 | 核心内容 | 必须可见的异常状态 |
| --- | --- | --- |
| 收件箱 | 上传、原图、识别草稿、校正文本 | 上传失败、识别超时、重复输入、未保存 |
| 确认页 | 新建或关联事项、日期/材料/责任人证据、关键澄清 | 不确定日期、同名不同活动、来源冲突 |
| 变更预览 | 前后值、新增/撤销要求、受影响计划、完成复核、确认/放弃 | 提案已过期、缺少关键答案、无实际变化 |
| 任务板 | 待处理、进行中、需复核、已完成、已取消；负责人、材料缺口 | 交接等待、准备时间不足、日历导出过期 |
| 任务详情 | 原通知与历史、要求状态、计划、交接、完成记录、ICS | 历史完成不覆盖新版要求、外部结果未知 |

用户用语：显示“已提醒”“你记录已提交”“待对方接手（尚未联系）”“你记录对方已接受”。不要把这些都叫“成功”。产品中不暴露 token、schema、乐观锁等实现词；冲突提示写“任务已发生变化，请查看更新后的预览”。

## 澄清策略

只问会改变行为的关键问题，优先级为：是否同一事项 → 是新要求还是替代要求 → 精确截止日期/时间 → 负责人或交接 → 准备安排。每次最多 3 个问题，允许保存草稿后离开。不确定的截止时间不得阻塞阅读和整理已知材料，但阻塞精确时间提醒、ICS 时间事件与正式采纳截止变更。

对于“周五前”等边界模糊表达，询问具体日期、是否含周五及时间；若用户选择仅记录日期，保留 date-only + 边界说明。模型自报置信度只能排序提示，不能跳过确认。

## 可用性与试用边界

桌面与手机窄屏可用；所有关键信息不只靠颜色；操作可用键盘；上传有尺寸限制与进度；失败保留草稿。MVP 只监听 127.0.0.1，使用者为本机单用户。邀请测试者时使用合成或脱敏通知，或单独本地实例；公开部署和真实多用户测试需要另开身份、隔离和运维阶段。
