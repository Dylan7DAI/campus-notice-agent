# 验收、模型评估与用户试用

所有门槛都是本项目的**预设目标**，不是实测结果。当前只交付设计场景与规格检查；测试 runner、模型成绩、用户实验尚未实现/开展。

## 四层验证必须分别报告

1. **规格检查**：JSON可读、引用存在、场景结构完整。不能证明业务功能。
2. **确定性产品测试**：纯函数 + 真实临时 SQLite/API + 浏览器。Mock 可隔离模型，但不能证明识别质量。
3. **真实模型评估**：输入真实的合成截图/脱敏通知，记录提取、关联、提案质量及多次运行波动。
4. **用户试用**：实际操作者能否发现变化、修正错误、理解完成与交接。不能由模型自评代替。

## 回归场景 E01–E24

[scenarios.json](../evals/scenarios.json) 给出固定输入、动作和预期，绑定规范见 [场景使用说明](../evals/README.md)。它是可转测试的设计语料，尚不是可执行的应用测试。M3 编写 runner 将 given 导入隔离数据库、when 映射到真实应用命令，并将每个 expect 对照真实状态；不能仅检查 JSON 里存在 expect 就报 passed。

| 分组 | 场景 | 核心观察 |
| --- | --- | --- |
| 更新一致性 | E01–E06、E24 | 稳定 ID、材料集合、旧版完成覆盖、真实变更 |
| 执行与责任 | E07–E09、E20 | 提醒/准备/接手/完成的区别 |
| 解析与证据 | E10–E13、E22 | 不确定性、来源冲突、校正记录、伪引用 |
| 事务与恢复 | E14–E17、E23 | 过期提案、幂等、回滚、取消恢复、补偿 |
| 模型边界 | E18–E19 | 注入、超时、非法结构不改变正式任务 |
| 导出 | E21 | UID、sequence、stale、取消状态和客户端局限 |

critical 场景必须全部通过才进入试用；任何无确认更新、错事项合并、完成证据丢失、半事务或数据泄漏都阻断交付。对 schema 加非法字段、假证据、无offset时间、越界ID等负例；这些是实质性边界测试，不写只照抄实现的快照测试。

## 数据与标签计划

先准备30个互不重叠事项的通知序列，每个2–4条，覆盖三种业务以及取消、歧义、乱序、同名不同事项。按事项划分20个开发集、10个封存评估集，不按单张截图随机分割同一事项。另保留 E01–E24 作为确定性规则回归，不混入模型评估成绩。

数据最初以合成/取得同意的脱敏材料为主，标记来源类型，不能把它们称作真实校园大规模数据。至少两人独立标注关键要求、日期精度、版本关系、应更新字段、不应更新字段、应澄清事项和正确证据；分歧经讨论形成固定 gold。原文本身无法判定的项目 gold 为 needs_clarification，不强行编造唯一答案。

每例固定发布/接收时间、时区、既有任务、负责人、完成记录和用户答案。图片质量分清晰/截断/模糊三组。保存图像到访问受控的数据目录，公开 repo 仅放合成数据或不可还原的 case ID。

## 主要指标与分母

| 指标 | 计算方法 | 解释 |
| --- | --- | --- |
| 漏项率 | gold要求中未在最终active要求正确表示的数量 / gold active要求总数 | 同时报每个任务平均漏项数，避免长清单主导 |
| 错误更新率 | 有至少一个错误字段改动或错事项合并的更新尝试 / 需要处理的更新尝试总数 | 另报错误字段数、错误合并数；不能只统计已成功提交样本 |
| 提案错误率 | 人工纠正前含错误操作的提案 / 生成的提案 | 防止依靠用户兜底掩盖差的模型建议 |
| 虚假完成数 | 当前条件未满足但UI显示已满足新版完成的任务数 | 关键门槛，目标0；审计自动判定并人工抽查 |
| 证据正确率 | 可定位且语义支持该字段的事实 / 被采纳事实 | 字符串存在不等于语义支持 |
| 适当澄清率 | 该澄清且确实澄清的案例 / gold需要澄清案例 | 同时报无必要澄清率，避免逢事必问 |
| 校正时间 | 用户看到草案到正确确认的秒数 | 记录主动操作时间、等待模型时间、失败/退出；报告中位数和IQR |
| 操作负担 | 点击/修改字段/澄清问题数 | 与漏项一起看，不以少点击牺牲正确率 |
| 运行性能 | p50/p95耗时、调用数、可得token/费用、失败率 | 冷启动/热运行分开；未知费用标unknown |

“错误更新数量”至少分为提案错误（被用户拦下）和落库错误（实际破坏状态），两者都报告。用户审核可使落库错误接近零，但不代表智能提案准确。对 aborted/timeout 单列数量，并纳入任务成功率分母，避免只保留成功案例。

## 对照与消融

工程验收用代码判定状态。产品效果先做小规模试点：8–12位学生，每人执行三条件各2个难度匹配的事项序列，顺序平衡、素材互换，避免记住答案。条件为 A 手动清单，B 一次性通知抽取到任务（后续变化由人处理），C 本系统。固定通知内容、允许的时间和完成标准，记录材料漏项、错误更新、校正时间与理解性访谈。

如果要解释机制，在能负担时另做 C 去掉证据/差异展示的消融，或 C 去掉完成覆盖检查的离线消融；不要一次增加太多实验条件。与 Donetick 做实测比较前须安装并记录版本、配置与语言支持，不能把自己简化的B直接命名为Donetick。

这是可用性和可行性试点，样本规模不足以直接支持普遍优越性。优先报告配对差值、分布、失败案例；如需论文推断，按试点方差重新做样本量规划，获得所需研究审批/参与同意。

## 准入与止损

- M3：24项确定性回归全部通过；关键事务/注入/误完成负例均为0次错误提交。未实现项计未通过。
- M4：封存集首次运行无错误自动提交；关键事实准确率目标≥95%、证据正确率≥95%、需澄清召回≥90%。规模小必须同时报告 numerator/denominator 和区间，不能把0次观察错误解释为真实风险为0。
- 模型/prompt版本变化：同一封存集至少重复3次，报告各次及“3次均正确”的事项比例，不挑最佳一次。
- M6/M7：用户能独立跑完主路径；严重误理解为0；目标是相对B降低漏项/更新错误且不过度增加校正时间。是否达到由试点数据决定，不先写结论。
- 止损：若连续两轮迭代仍严重错连事项，缩小为用户显式选原任务；若OCR主导错误，保留校正文稿步骤；若新增材料无法可靠识别，优先保住证据/人工确认功能再扩域。不要靠换名称宣称问题已解决。

## 结果文件合同

M3/M4 runner 输出 `evals/runs/<run-id>/summary.json`（Git忽略），包含 git_revision、model/provider/prompt/schema版本、fixture hash、clock、每例actual/expected/diff、pass/fail/not_run、耗时与费用。失败 trace 默认仅含合成数据/ID；人工校验用固定 rubric。进度文档只链接本机可用报告并记汇总，绝不提交个人原通知。
